# Gherkin step contract and fixture recipe

The two files under `features/` contain 12 B scenarios and 12 F scenarios, each with a stable tag. They specify public observations for a black-box runner; this document defines their setup, synchronization, and assertions. They are not an implementation test suite or hidden-test disclosure. All scenarios apply unchanged to E and G. SPEC.md and PROTOCOL.md settle field, exit-code, file, and timing assertions; no implementation-internal hooks are used.

## 1. Isolation and common vocabulary

Every scenario owns one temporary root with `data/`, `work-w1/`, `work-w2/`, bare `r1.git` (and optionally `r2.git`), and **fixture-owned** `control/`. Reserve an unused localhost port, close the reservation immediately before launch, and retry fixture setup on an unrelated bind race. A restart uses the same data, work paths, repo paths, and port. Start daemons as separate OS processes and retain their actual PIDs and stdout/stderr pipes. Never identify processes with a broad name search. There are no remote Git URLs or host repositories.

Initialize a scratch non-bare author checkout inside the temporary root, configure deterministic fixture Git identity, create branch `main` containing `common.txt` with `original\n`, commit, and clone it as bare `r1.git`. Read its base with Git and substitute the actual full object ID for `base1`. Set the bare symbolic HEAD to `refs/heads/main`. Do the same independently for `r2`. Repository paths containing spaces are an additional valid fixture variant. The harness's author checkout is not a product workspace and is never submitted as `repo`.

Generate patches by editing the author checkout based at the base, staging the intended additions/modifications/deletions, and taking a binary-capable Git diff against the base. Encode that diff as a JSON string; do not pass the patch filename as `patch`. Ordinary success adds `jobs/JOB_ID.txt` containing the ID. Nonconflicting jobs add different files. A rebase-conflict pair modifies the same line in `common.txt` to two distinct values. A patch-failure input refers to a nonexistent preimage/context but remains a string accepted at submission.

"Fresh data" means no preexisting state; "ready" means the specified JSON stdout readiness line was received within the 10-second SPEC.md startup bound and its PID is the launched live process. There is no fixed startup sleep. Before sending jobs, confirm status can connect. With no workers ready, accepted jobs remain queued. Statements assuming a particular owner start only that worker, wait until it owns the job, then start the second worker; they do not rely on a race between two free workers.

## 2. Command and protocol observation steps

Run a client with an argument vector, not an interpolated shell command. Capture exit status, stdout, and stderr separately. Parse exactly one JSON line where the CLI contract calls for JSON; assert no extra progress output. For plain status assert the exact header and field order and parse tab-separated rows. Filesystem paths in scenarios are replaced by their canonical absolute values.

"Complete base job record" means exactly the 11 required keys in SPEC.md, with their specified types/null rules: `id`, `repo`, `seq`, `state`, `attempt`, `worker_id`, `lease_expires_at_ms`, `accepted_at_ms`, `updated_at_ms`, `landed_commit`, `reason`. Validate all keys, not only state. Check positive sequence, nonnegative attempt, timestamp monotonicity, known state/reason combinations, landed_commit only when landed, and terminal ownership/deadline null. Check every status array is sorted by seq with unique IDs/sequences. Save terminal records and compare the **entire** record after restart; heartbeat or duplicate requests cannot update terminal timestamps. MAINTENANCE.md extends the record with `priority` for maintenance snapshots.

"Submit" writes a UTF-8 JSON input file and invokes the specified submit command. It asserts acceptance before later work. For B03 reorder object keys and formatting without changing values; optional canonical-path alias replay uses a symlink while it still resolves to the same repo. For B04 change only patch to make ID_CONFLICT unambiguous. Invalid timeout and unknown-flag probes use separate IDs/calls, and must neither consume sequence nor change the accepted input. CLI invalid JSON and unknown/missing/duplicate flags are governed by the same exit-2 decision even if not separately scored.

"Wait exits ..." invokes wait with a sufficiently large caller budget, then asserts the terminal outcome/reason and relevant output. Default fixture completion budget is 30 seconds; use up to 60 seconds for recovery with multiple eight-second lease periods. These fixture budgets are failure timeouts, not extra product guarantees. A timeout_s zero wait returns immediately as specified; do not assert that it waits for a scheduler tick. NOT_FOUND has no stdout and has the specified stderr error object.

For direct protocol steps open TCP, send a complete object and LF, read one LF-delimited response, and validate envelope/correlation fields. Worker fixtures use the specified register/poll/heartbeat/result messages, not private APIs. The F05 fixture owns a work lock and installs containment before doing any actual execution; preferably it executes no command at all and fabricates no successful artifact. It saves its real leased input, attempt, token, and checkout path, then stops renewing. Its old unsaved build/ok result uses a syntactically valid commit ID and saved path; fencing must reject it **before** artifact acceptance. At expiry an obsolete session may yield STALE_SESSION rather than STALE_LEASE. The replacement is observed before stale messages are sent, and its record/target remain unchanged by them.

When checking snapshot layout, read `data/state.json` in one open/parse, allow an old or new complete snapshot during mutation, and poll for an acknowledged transition if the read raced. Verify exact top-level version/next_seq/jobs/repos shape, entry input/record/internal, repo/ref/intent, ordering, normalized inputs, and the required intent fields. Never compare a status response and a later file read as if they were an atomic pair. On a stopped coordinator, save one immutable snapshot for recovery assertions. Optional `internal/` files and OS lock contents are never parsed.

## 3. Gates and build invocation accounting

Provide a fixture build helper at an absolute path under `control/`. `build_cmd` calls that path using correct shell quoting. The helper records a monotonically increasing invocation number, PID identity, start time, completion/exit, and selected checkout file contents in fixture-owned storage, **outside** the product checkout. Use atomic writes/append locking for concurrent helpers. The helper prints a unique known token to stdout and another to stderr. A success token is recorded only after its checks and gate pass; a crash can leave a started invocation without completion.

An external gate is a file or pipe the helper waits for, using short polls while remaining interruptible. It writes a separate `started` event before waiting. Tests observe BOTH the helper event and the appropriate public running/landing state before injecting a fault. Releasing a gate modifies fixture-owned control state, not product data or Git. Gates distinguish initial and landing invocations with an external counter for that job. In no-fault B02 there must be exactly two started/completed successful invocations. Retries may legitimately add more initial/landing invocations, so F tests never assert a fixed total after a crash.

For B06 hold j1's first invocation, submit j2 and wait until j2 is ready. Both attempts must be positive and owned by distinct workers; do not require observing j2's possibly brief running state. While j1 remains gated, stable target head is base1. Release j1, wait for both terminal records, and inspect history for j1 then j2. Polling cannot prove absence of every transient overlap; the sampled at-most-one-landing assertion is supplemented by final commit order and the Quint invariant.

For B07 keep j1 gated on r1 and run a passing j2 on r2 using the free worker. Observe j2 landed before releasing j1. Cleanup after the scenario cancels/releases j1. This asserts independence of repositories, without requiring a particular concurrent scheduler.

For B11 j1 adds `forbidden.txt`; j2 changes an independent file and its build checks that `forbidden.txt` is absent. Hold j1's initial invocation until j2 is ready. Release j1 so it lands first; j2's initial checkout had no forbidden file, but its rebased landing checkout does. Both invocation records and the rejected landing record must match. This detects omission of the mandatory second build.

A gate used in F01/F02/F04/F09/F11 is released or switched to allow **future** invocations after fault injection, so a replacement can finish. Use separate start events per invocation and never mistake a stale event for a new attempt. F12's second job has a quick successful initial invocation and a two-second hanging landing invocation; each gets its own command budget.

## 4. Git and landing assertions

Read target HEAD with Git on the bare repository. Compare the branch, not FETCH_HEAD, private worker branches, or object-count growth. A successful job's `landed_commit` must occur exactly once on the target branch, have the required subject and author/committer identity, and be a direct child of the previously observed accepted lane head. A one-job success has exactly one additional commit beyond base. Two ordered independent additions have subjects j1 then j2 in chronological ancestry order and preserve both source effects. Failed/rejected/cancelled/timed-out jobs have no subject/patch effect on the target; their private objects may exist and are not counted as lands.

B08 skips a failed FIFO predecessor and observes the later success. B10 asserts j1's effect remains and j2's conflicting effect does not. B11 asserts the rejected j2 contributes no commit despite a successful initial build. Do not assert exact commit IDs across implementations, timestamps, implementation-private refs, or rebase diagnostics.

F03 deliberately races crash against releasing a successful landing gate. It may catch: an unprepared rerun, a prepared intent before ref movement, ref movement before terminal persistence, or an already durable landed record. All are legal crash points; recovery must produce the same exactly-once outcome. If a prepared intent is actually observed, save its candidate and assert it is the recovered landed_commit. Do **not** require an external poller to reliably catch a microsecond-wide prepared window. The two directed Quint recovery tests cover those abstract windows without private fault hooks. Record which point was caught for diagnosis; repeatability of every scored OS test is subject to the design's 3/3 two-host witness passability gate. No claim of real-storage crash-window coverage follows from a model check alone.

## 5. Descendant fixture and liveness checks

The process fixture must exercise actual descendant relationships, not merely an unrelated daemon. Start a direct child of the job command, a child that calls setsid, and a double-fork child whose intermediate parent exits so that it is reparented. Long-lived descendants install no cooperative cancellation handler and loop indefinitely. At least the detached/double-fork long-lived descendant continues a short-interval heartbeat to `control/`; this proves it is alive and doing work before the fault. Include a descendant that ignores SIGTERM, requiring forceful cleanup. Intermediates that intentionally exit are historical evidence of ancestry, not members of the stable live PID set.

Each long-lived process atomically registers its PID and OS start-time identity before writing readiness, then emits heartbeats. For every tree, wait for the expected stable long-lived set plus double-fork evidence, verify those identities are live, and only then inject the fault. Retain the launched shell/helper identities too, if still alive. "Full registry confirmed alive" means this expected stable set, not intermediates that already exited normally. Use fixture-owned locks so racing PID registrations cannot overwrite entries.

Dead means that exact PID/start-time identity is absent or no longer executing (a zombie awaiting OS reaping is not a live executing child); require its heartbeat to stop as a secondary check. A reused PID belonging to another start-time identity is not the original descendant. `kill(pid, 0)` alone is insufficient because it can report zombies or a reused PID. Use local OS process-table observations and start-time identities; no platform-specific product API is required. In F04/F11, timestamp the replacement command's start and verify all old live identities ended first. In F06/F07/F08/F09/F12, enumerate **all** registered stable identities, not just the child nearest the shell. Cleanup checks include descendants that have changed session or been reparented.

Observe a renewal immediately before a worker kill by reading two successive public deadlines, then save the newer expiry from status. Capture monotonic fault time and the simultaneous UTC value to translate that public Unix deadline to the harness's monotonic deadline. Never estimate a fresh eight seconds from worker death if the recorded lease has less remaining time. No heartbeat after the kill can renew that worker's lease. For both-process death save the deadline before either kill and do not restart anything until after the containment assertion, proving independence of restart.

Connected cancellation's cleanup bound is two seconds from the acknowledged cancellation decision/response; the earlier hard lease deadline still applies. Command timeout's cleanup bound is one second after the helper's observed command start plus input timeout_s. Lease death is due by the stored hard expiry; requeue/assignment visibility is due by expiry plus one second while the coordinator is available. Allow at most 250 ms for observation scheduling and poll at 50 ms or less near deadlines. Record actual elapsed times. A slow fixture or missing readiness fails fixture setup; it does not justify silently stretching the product deadlines.

## 6. Fault and restart procedures

SIGKILL uses the launched recorded PID; wait for OS process death before restarting that same daemon. Keep reading its saved stderr pipe as diagnostics, but never assert log wording. Verify another live coordinator cannot share `data/`, and that the dead coordinator's stale lock file does not block recovery. Restarts must emit readiness before CLI calls. Job leases and independent containment continue expiring during coordinator downtime; availability assertions resume once the coordinator is ready. Exact terminal-record equality applies to F10, not to nonterminal records whose owners/states legitimately change during F01/F02.

F01 gates the initial command; F02 gates the second command and observes landing **before** any intent. Neither relies on sampling a fleeting state. The restarted coordinator cannot renew an old session: old attempts are cleaned and expire/requeue under their original deadlines. A reconnected/new worker can take the retry after cleanup. F03's allowable race cases are defined above. F04 and F08 keep the coordinator alive. F09 keeps both coordinator and killed worker down until cleanup has been proved.

F11 SIGTERM is a graceful worker stop. Its exit 0 plus empty old tree is observable, and the worker must exit within the SPEC.md two-second shutdown bound; shutdown protocol acknowledgement can be captured through the fixture's protocol peer or approximated conservatively by the worker exit time. The one-second retry assertion using worker exit time is weaker than the acknowledgement bound; document this when the product worker's internal traffic is not visible. Do not infer a released lease merely from SIGTERM delivery.

For F10 save both terminal JOB_RECORDs, the snapshot's next_seq, and target head/history, then perform three SIGKILL/readiness cycles. Compare all saved terminal fields and ordering after each cycle. A new j3 receives the saved next_seq; it need not finish to demonstrate preserved allocation. For F12 ensure the snapshot has no prepared intent before issuing cancellation while the rerun is still gated; keep it gated until descendants die so a candidate cannot win legitimately.

## 7. Runner hygiene and scope

Scenario teardown stops only its own recorded daemon/helper processes, force-kills any surviving registered fixture descendants after recording a failure, and waits for them to stop before removing temporary paths. Do not rely on teardown cleanup to satisfy a containment assertion. Dispose of temporary repositories only after all commands and independent fixture containment processes are stopped. No changes are committed outside these scratch fixture repositories.

Treat readiness, stable gate states, registered live identities, and target ancestry as synchronization. Avoid arbitrary sleeps for job ordering or crash injection. Scored tests use the DESIGN-ARCH.md witness passability gate and repetitions; features do not override it. Neither this document nor the formal model asserts that actual B/F tests have passed until a witness has run them on both hosts.
