# Diagnosis before application patch

The violated property is `cleanup_gate`: `cleanup` and `retry` may clear
`work` and `pending` only when both `pending` and `saved` are true. Otherwise
all fields must remain unchanged, including pending cleanup after a failed
preservation.

Baseline `./fv check` (cycle 1) regenerated the current application and reported
`success`, `failure`, and `retry_idempotent` PASS, but `cleanup_gate` FAIL
(3/4 laws). Lean's `decide` established that `check_cleanup_gate = true` is
false. The starter test passed; it covers successful preservation only.
The source trace reaches `cleanup_ready/1` at `app/lib/preservation.ex:48-49`
and `retire/1` at lines 52-53 via the event dispatch and cleanup helpers.

The causal function is `Preservation.cleanup_ready/1`: it returns only
`state.pending`, omitting the required `state.saved` guard. `retire/1` correctly
performs the requested retirement; its caller incorrectly permits it without
a preserved copy.

A concrete witness derived directly from the source is:

1. `init()` gives `%{work: true, saved: false, pending: false}`.
2. `step(state, :preserve_fail)` gives
   `%{work: true, saved: false, pending: true}`.
3. `step(state, :cleanup)` (or `:retry`) currently gives
   `%{work: false, saved: false, pending: false}`.

The required result at step 3 is the unchanged state from step 2. Thus the
application loses the sole work copy. The fixed all-boolean-state domain also
exposes the bug immediately for any state with pending true and saved false.
This is an implementation defect, not an unresolved proof or tooling limit.

Planned repair: make `cleanup_ready/1` require `state.pending and state.saved`,
retaining every public function and leaving accepted laws, domains, assumptions,
and bounds unchanged. Add regression tests for failed preservation followed by
cleanup/retry and for cleanup/retry across all eight boolean states, then run
`./fv check` to regenerate the formal representation from the changed source
and check the fixed laws and tests.

# Repair and verification results

The application patch changes only `cleanup_ready/1` to return
`state.pending and state.saved`. The public API and all other transitions are
unchanged. Generated `verification/Implementation.lean`, `verification/ir.json`,
and `verification/source-map.json` were regenerated by the supplied checker;
the generated guard now contains `v_pending && v_saved`.

The harness treats the entire test directory as frozen. Cycles 2 and 3 rejected
attempts to extend regression coverage before regeneration or proof checking
(exit 2). Those test edits were removed, and the supplied starter test was
restored byte-for-byte. These were harness input restrictions, not application
counterexamples or Lean proof limitations.
