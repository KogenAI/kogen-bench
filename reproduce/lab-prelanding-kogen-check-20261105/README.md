# An unconditional kogen check at landing fails its rule: it refuses known-good commits and reproduces 1 of 8 breakers for the reported reason

Finding `lab-prelanding-kogen-check-20261105`. A model-free Lab (no model call, no seat, 5 Nov 2026) on one question: would a kogen consumer check that is never skipped (no "no exported interface", no fast-forward skip, no bare-loop skip) have stopped the commits that broke kogen's tests, without refusing commits that were fine? The Studio Lab record is `lab-prelanding-kogen-check-20261105` (registered 5 Nov 09:49Z before the first run, the result is in a later revision).

Arms, on the same 48 component landings of 3 and 4 Nov:

- **A**: the landing gate as it decided, read from the land logs (no re-run). All 48 landed GREEN. Kogen's own tests ran at landing for 1 of the 8 breakers (shaping 1e795ed, `go test` only); the other 7 were skipped as "no exported interface" (2), "fast-forward" (2) or "still requires the bare kogen-loop" (3).
- **B**: the unconditional check. A scratch copy of kogen main as it was at the landing time; the landed commit pinned the way the adoption does it (`go get` and `go mod tidy`; for kogen-loop `sync-kogen-loop.sh` and the module rename); then `gofmt -l`, `go build`, `go vet` and `go test ./...` in `cli/`, including `consumes/*`, `TestLoopPin` and `TestAssemblyUsesThePinnedComponents`. A failure refuses the landing only if the same test passes on that kogen main without the pin (the base). A commit that cannot be pinned or built counts as red.

Sample (`data/sample.tsv`): the 8 breakers named in the 5 Nov adoption review (build 8852812 and 10f190b, coordinator 91d0a32 and bc5b726, shaping f04edce and 1e795ed, setup aeeb5be, review f4b7f54) and 40 known-good landings drawn with `random.Random(20261105).sample` from the 84 green landings whose first release is 41d70052 or d98cfe01. The good commits run in draw order, so the 31 that ran are themselves a random sample of the 40.

Registered pass rule: B refuses at least 6 of the 8 breakers and at most 2 of the 40 good commits.

Median cost: **4.8 minutes** added to a landing (pin, gofmt, build, vet and test on one 2-vCPU host with a warm Go build cache; 4.8 with the wait for the shared Go lock, which was 0 in practice).

## Diagnostic: pin the tuple the next adoption would pin (post hoc)

The review's windows moved all components together. On the rows whose era allows it, the same steps with the tuple "landed commit plus every other component's main head at that time" (loop-free tuple where the heads mix old and new loop paths) give: 5 breakers run, 5 refused (strict), 2 for a kogen test or vet failure (coordinator 91d0a32: `TestResearchRemovalDefaults`; shaping f04edce: kogen's test code no longer compiles against the executor head, `undefined: agent.Reviewer`), 2 unbuildable through loop-module skew. It also refuses 6 of the 6 good commits tried, all for kogen tests that kogen itself edited before the release (`TestApproveDeadline*`, `TestResearchRemovalDefaults`, a vet error in a kogen test file; kogen 96b7438 and 896ae0c). So the tuple variant does not separate breakers from good commits either: at the landing-time kogen main, kogen's tests lag every tuple move, and the real adoption carried the kogen-side edit in the same pin. A tuple failure is also attributed to the tuple, not to the commit that triggered the check.

## Verdict

**No.** The unconditional single-commit check, run as registered, fails the pass rule on false refusals, and it also fails on recall under both post hoc readings (4 and 1 of 8). Of the 8 breakers it reproduces 1 for the reported reason (build 8852812, `consumes/kogen-build` TestRecover*). No DELIVERY.md is written. What the data supports instead: (1) the cost is small (about 4.8 minutes); (2) a landing-time check cannot tell "a component broke kogen" from "kogen's tests lag a legitimate component move": in this window the adoption itself carried kogen-side test edits (96b7438, 896ae0c), coupled components need to move together (an executor change breaks the unmoved build module), and the tuple variant refuses the good commits as well, so any such gate needs the kogen-side change to travel with the pin or kogen's tests to be pin-agnostic; (3) it needs a kogen main whose tests follow the pins (true since 896ae0c) and which has finished the loop-module move; (4) acceptance-only breaks need the acceptance suite.

## Limits

- Arm B pins one commit onto kogen main as of the landing time and stops at kogen's go level; the landing times come from the land logs' `done` stamp and the last first-parent kogen commit at or before it.
- 31 of the 40 good commits ran (random prefix); the adjusted and behaviour readings are estimates from those. The strict verdict does not depend on the rest.
- The host is a 2-vCPU Linux box without zsh; one test fails on every base for that reason. Timings come from a host shared with other Labs and with delivery; load was recorded per run in the Lab log, not controlled.
- The tuple diagnostic is post hoc, covers 11 rows, includes unqualified model-facing heads, and was not registered.
- 4 of the 8 breakers' original failures were read from the adoption step outputs, not re-observed.
