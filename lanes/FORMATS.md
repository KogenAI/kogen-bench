# Formats

The contract every lane package follows. All JSON is written with sorted keys and a trailing newline (`common.write_json`).

## Kogen (what the harness relies on)

Studied at Kogen `b45ba32b` (read-only). Paths are in the Kogen repo.

- **CLI** (`cli/main.go`: `parse` l.97–190, `main` l.222–284): `kogen version` (also `--version`), `kogen init`, `kogen intent shape <slug> <request-file|->`, `kogen intent approve <slug> [<hash>]`, `kogen intent build <slug>`; `shape`, `approve` (also `--by <name>`) and `build` take `--project <dir>` (default: the current directory, which must be a git work tree); `init` and `version` take **no options** (`init --project X` exits 2 with `unknown option '--project'`) and `init` always runs in the cwd (`cli/main.go` l.77–90, 272–273). Slug: 3–48 chars, lowercase letters, digits, dashes (`cli/main.go` l.95, 241–246). `<hash>` is 6–64 lowercase hex.
- **Output**: results and errors go to stdout; errors are one line `<class>/<reason>: <detail>` (`lib/kogen/error.ex` l.1–15); progress goes to stderr (`docs/configuration.md` l.36).
- **Exit codes**: 0 success; 1 refusal or failed build (`Error` default, `build.ex` l.592, 827, 852, 932, 1009); 2 usage or invalid input (`main.go` l.225, 243; `approve.ex` "approval_identity_unavailable"); 3 environment (`build.ex` l.33, 896; `main.go` l.230); 5 `approve` without a hash printed the review card (`approve.ex` l.154); 70 internal error (`lib/kogen/main.ex` l.51); 129/130/143 signals (`main.ex` l.57–59). Build outcomes beyond "landed" are named only in the run log, not in the exit code.
- **Version**: `kogen <sha8> (<date>)` or `kogen dev+<hash8> (<date>, uncommitted source)` (`lib/kogen.ex` l.7–10).
- **`kogen init`** (`lib/kogen/init.ex` l.20–60, 83, 154ff; `README.md` l.48–60): needs a git identity (`Git.identity!`, l.20). On a repo with commits it makes **one shaping-model request** (`ChatGPT.require_login!`, detection of the project's commands), so its `commands` can differ between cells and it costs a model call; it then writes `.kogen/project.yaml` and `.gitignore` (adds `.kogen/local/`) and commits both as `Add Kogen configuration`. On a repo that already commits `.kogen/project.yaml` it only prints `Kogen is already initialized in <root>` and exits 0. On a repo without commits it writes a template and commits it. **The harness should ship a fixed, committed `project.yaml` (and `.gitignore`) with each task or lane and not run `init` per cell**; that avoids the model call and the variation.
- **Project config**: `.kogen/project.yaml` (`docs/configuration.md` l.19–22, 32): `version: 1`, `commands:` (setup, fix, checks, acceptance), `protect:`, then `models:` with `shape`, `build`, `review` (also `read`, `probe`, `draft`), each `{model: <name>, effort: <effort>}`. No command takes model flags. A lane's `"provider/model effort"` string maps to one such line (the provider part is not in the file at `b45ba32b`; the harness writes `model: <provider/model>` unless L2 finds Kogen wants the bare name).
- **Intent**: `.kogen/intents/<slug>/` with `intent.md`, `acceptance.feature`, optional `model.qnt` and the step files it names (`lib/kogen/intent.ex` l.1–26). `shape` writes it uncommitted; the Intent folder must be committed or untracked-but-present at build.
- **Approval**: `kogen intent approve <slug>` prints the card with `SHA-256: <hash>` and exits 5; `approve <slug> <hash-prefix>` writes `.kogen/local/approvals/<slug>.json` `{slug, sha256, approver, approved_at}` (`approve.ex` l.60–100, `intent.ex` l.353) and exits 0. Needs git `user.name`/`user.email` or `--by`. The approval is deleted when the build lands (`build.ex` l.940).
- **Run log**: `.kogen/local/runs/<id>/` (`lib/kogen/run.ex` l.1–25) with `log.jsonl` (one JSON object per line, each with `at` ISO-8601 UTC and `event`), `result.json`, `review-<n>.json`, `checkpoint.json`. Events: `start` {slug, start_head, approved}; `request` {role, model, effort, usage (the provider's usage map as Kogen has it; Kogen counts input, cached, output, reasoning), wall_ms} (`build.ex` l.1128); `tool_call`; `command` / `command_result` {name, status, output}; `pass` {pass, green, failing, not_run, files_changed_while_checks_ran} (`build.ex` l.734); `review` {review, attempt, pass, tree, verdict, findings} (`review.ex` l.135); `commit` {tree} (`build.ex` l.875); `builder_blocker`; `resume`; `outcome` {outcome, commit?, provider_failure?} (`build.ex` l.944, 1068). `result.json`: {slug, build, outcome, start_head, passes, reviews, repairs, usage, model_active_ms, ...} (`build.ex` l.1082). A landed build is one commit on HEAD.
- **Not in b45ba32b** (what the design's R1–R5 would add): tree hashes on `pass` events (only `review.tree` and `commit.tree` name trees); per-stage start and end times (only `at` per event and `wall_ms` per request); unknown per-request usage is not marked; building from a supplied, already-approved Intent without shape; `version` reporting a dirty-tree hash for patched builds; distinct exit codes per outcome (timeout, blocked, provider failure). Until then the harness derives pass trees from `review`/`commit` events and outcomes from the last `outcome` event.

### The Go Kogen (`687f1407`, read-only; `d0bc4af0` is the same layout)

One cell runs against either CLI; the commands, the card, the paths and the usage keys are the ones above. What differs (`cli/…` at `687f1407`):

- **Build** (`lanes-build`): no root `go.mod` and no `mix.exs`; the module is `cli/go.mod`, the release is `packaging/package.sh` (l.1–6, 88–90: needs Go and Node/npm, no Erlang; prints `dist/kogen-<version>-<target>.tar.gz` holding `bin/kogen`, `lib/`, `install.sh`). Layouts, first marker present wins: `mix.exs`, `cli/go.mod`, `go.mod`. The first two share one builder: it checks `go` and `npm` on PATH for the Go layout (a missing one fails with its name before the script runs), runs the script and takes the one archive from `dist/`. The script runs `npm ci`, so a first build needs the network; targets are darwin-arm64 and linux-x86_64 only. A patched tree is uncommitted, so its `kogen version` is `dev+<hash8>` (`package.sh` l.21, 32; the hash covers `LICENSE NOTICE cli packaging docs`); the lock records the patch hash, so that is enough.
- **Install root**: `bin/kogen` finds its root as `dirname(dirname(self))` and reads `<root>/node-path` (`cli/main.go` l.263–272, 373–382), like `install.sh` writes it; `release_root` / `ensure_node_path` apply unchanged.
- **CLI** (`cli/main.go` l.20–52, 94–106, 112–227): also `refine`, `recover`, `resume`, `list`, `usage`, `inspect`, `preflight`, `context`, `provider`; the harness uses `version`, `intent shape|approve|build`. `intent build` also takes `--context <file>`, unused. Slug rule l.298 as above.
- **Exit codes**: as above plus 4 (provider: usually no saved login for a role's provider, `provider/not_signed_in`-style from `RequireLogin`, `cli/provider/creds.go` l.127, which `shape` and `build` check before any request; also `provider/refused`, `cli/provider/respond.go` l.151) and 5 also for a build on a dirty tree (`environment/dirty_tree`, `cli/build/build.go` l.148–170: only the Intent's folder, its acceptance files and other Intents' folders may be uncommitted; `shape` of an existing slug is `intent/exists`, 5, `cli/shape/shape.go` l.104–107). Login, tool, config and dirty-tree errors exit before the run log exists (`build.go` l.226–237), so a build with no `outcome` event takes its outcome from the exit code: 4 `provider`, 3 `environment`, 5 `dirty_tree`, 2 `usage`, 70 `internal`, signals `signal`; exit 1 stays `no_outcome`, 0 `ok`. Shape and approve use the same table (`approve` exit 5 with a card is `ok`). Errors print `<class>/<reason>: <detail>` to stdout (`cli/native.go` l.55–68). Shaping `provider_call.usage` also carries the cache-write keys `write`, `write_30m`, `write_12h` (`cli/provider/usage.go` l.45), and for Anthropic `input` includes cache-creation tokens (`cli/provider/messages.go` l.451); `usage.py` does not read them (ISSUES).
- **Approval and Intent**: card `cli/shape/approve.go` l.403–405 (`SHA-256: <64 hex>`, exit 5); questions pending exit 5 `intent/questions_pending` (l.396), shaping questions `Questions for <slug>:` exit 5 (`cli/shape/shape.go` l.351); approval file `.kogen/local/approvals/<slug>.json` (`cli/project/baseline.go` l.167–178); Intent `.kogen/intents/<slug>/` (`cli/project/intent.go` l.45), `Slug:` line must be the folder's slug (l.260). Approve runs the readiness check, so the project's checks and acceptance run (no model request).
- **Project config** (`cli/project/config.go` l.56–59, 274–297, 360): `models:` roles are `shape`, `build`, `review` only (`plan` is ignored); any other role (`read`, `probe`, `draft` of the Elixir Kogen) is `environment/project_config_invalid` (exit 3). `provider` is `chatgpt`, `supergrok`, `opencode-go`, `anthropic` or `openai-compatible` (the last needs `base_url`, which lanes cannot set); a lane prefix `openai/` or `chatgpt/` writes no provider, which is ChatGPT. Commands keys `setup`, `fix`, `checks`, `acceptance{run, steps_dir}` as written by `project_yaml`.
- **Run log** (`.kogen/local/runs/<8 hex>/log.jsonl`, `cli/build/run.go` l.39–61, 79): the events of the table above with the same fields (`start` `build.go` l.283, `request` l.534 with `usage` {input, cached, output, reasoning} and `operation_id`, `pass` `cli/verify/run.go` l.229, `review` `review.go` l.300, `commit` `commit.go` l.42, `outcome` `commit.go` l.61 / `stop.go` l.118 with `provider_failure`), plus `stage_pass` {stage_id, stage_index, **tree**, green, failing, not_run} (`builder.go` l.326) for a staged build. Go Kogen builds from `3f032206` plus the logging patch name the verified tree on the `pass` event as `tree`; an older Go Kogen's `pass` carries no tree. `pass_trees` in `result.json` come from the `review`, `commit` and `stage_pass` events and from green `pass` events that carry a `tree` (see Run directory). Shaping events: `.kogen/local/shaping/<slug>/events.ndjson` (`cli/shape/evidence.go` l.53, `shape.go` l.75), as above.

`lanes/tests/fake-kogen` follows the lines above and nothing more; `FAKE_KOGEN_CLI=go` makes it act like the Go Kogen where they differ (config validation, `stage_pass`).

| `phase` | string | `shape` \| `build` \| `e2e` \| `probe` (a different shape of experiment: see Probe) |
| `intent_form` | string | `gherkin` \| `gherkin-lean` \| `gherkin-quint` \| `prose`; required when `phase` is `build` (the folder `supplied/<form>/` to build from), ignored for `shape` and `e2e` |
| `kogen.repo` | string | URL or path of the Kogen repository |
| `lanes[]` | objects | at least one; unique `name` |
| `lanes[].name` | string | as `id` |
| `lanes[].sha` | string | 40 lowercase hex, a Kogen commit |
| `lanes[].patch` | string or null | path relative to the experiment file, no `..` |
| `lanes[].settings.models` | object | role → `"provider/model effort"`; `.kogen/project.yaml` gets `<role>: {model: <part after the first "/">, effort: <last word>}` (bare id, as Kogen takes ChatGPT ids: `config.ex` l.19-21) for prefix `openai/` or `chatgpt/`, and `{model: …, effort: …, provider: <prefix>}` for any other prefix (e.g. `supergrok/grok-4.7 high`, `opencode-go/…`), only for roles set; the prefix `claude-code` (`"claude-code/claude-sonnet-5-5 medium"`) writes `{executor: claude-code, model: …, effort: …}` instead, see Claude Code executor. | `tasks[]` | strings | task ids, unique, at least one |
| `reps` | integer | ≥ 1 |
| `deadline_s` | number | > 0, per cell |
| `cost_cap_usd` | number | finite, > 0; required to run cells (`lanes-run`, `lanes-cell` refuse without it); the soft cap of the **ChatGPT-priced** spend, see Cost cap |
| `provider_caps` | object, optional | `{"<provider>": {"cells": N, "usd": X}}`, at least one of `cells` (integer ≥ 1) and `usd` (finite, > 0) per provider, never `chatgpt`; its shape is checked whenever it is present. Required only to start cells (`lanes-run`, `lanes-cell`): every provider a lane's `settings.models` names other than `openai`/`chatgpt` needs an entry, and a lane names at most one such provider besides `claude-code` (no models means ChatGPT). A run dir made before it existed loads without it for every read-only command (`lanes-report`, `lanes-export`, `lanes-cost recompute`, ...). See Cost cap |
| `hosts[]` | strings | host names only |
| `decision_rule` | object | has a string `kind` (L6 defines the kinds) |

### Climb experiments

`"kind": "climb"` marks a hill-climbing round (others: no `kind`). Extra fields, all required, validated by `experiment.py`:

| field | type | rule |
|---|---|---|
| `lanes[]` | objects | exactly two, named `baseline` and `candidate`, same `sha`; they differ by one patch (different `patch`, same `settings`) or by exactly one `settings` entry (same `patch`), never both |
| `split.train`, `split.test` | strings | non-empty, unique task ids, disjoint; together exactly `tasks` |
| `min_effect` | number | greater than 0, at most 1: the smallest pass-rate difference worth acting on |
| `noise_ref` | string | path to a noise record (written by `lanes-noise`; only its shape is checked here) |
| `round` | integer | ≥ 1 |
| `parent` | string or null | previous round's `id`; null exactly in round 1 |
| `decision_rule.kind` | string | `keep_revert` (and only climb experiments may use it) |
| `decision_rule.improves` | object, optional | `{"test": "task_sign", "max_p": p}` with 0 < p < 1: a split improves only if its pass-rate difference exceeds `min_effect` and the exact one-sided sign test over tasks gives p ≤ `max_p`, instead of a Hoeffding interval above zero (`DECISION-RULES.md`). Absent: the Hoeffding rule, report unchanged. With it the verdict adds `sign` (per split `k`, `n`, `p`) and its `params` is `{"improves": ...}` |

`report.json` of a climb run adds `climb`: per split (`train`, `test`) both lanes' `{correct, n, rate, ci}` (Wilson 95%), `unit` (`task`), `tasks`, `pairs`, `candidate_better`, `baseline_better`, `tied`, `difference` (the pass-rate difference: mean over tasks of each task's mean rep difference), `difference_exact` (the same, a decimal or `n/d`), `difference_ci` (Hoeffding 95% over tasks), `pair_difference`; `plumbing` (one row per excluded cell: `cell`, `lane`, `split`, `category`, `outcome`, which is null for test cells), `plumbing_counts`, and `train_failures` (cells of the train split that failed on the task, for the next round; test failures are never listed). Every lane also carries `pass_rate_ci`, `first_green_pass_rate_ci`, `plumbing` counts and `witness_failures_test` (climb: a count; the lane's `outcomes`, `classes`, `plumbing` and `witness_failures` then cover train cells only, and its rates leave plumbing out).

## Probe

`"phase": "probe"` runs cheap funnel steps (retrieval, ranking, a single model call) as commands over a corpus of items, with no Kogen. `lanes-plan`, `lanes-run`, `lanes-cell`, `lanes-preflight` and `lanes-report` take it like any phase; the code is `lanes/lanes/probe.py`. `lanes-export` and `lanes/reproduce.sh` handle a probe round: records per ok cell, `commands.json` and `commands/` (every script a command names, wherever it lives, copied and hashed in `PLAN.json`; an interpreter, that is a binary executable or a file with a known interpreter's name such as `python3` or `node`, is named with its `--version` output and not copied), a results table, and `--publish-private --corpus` for the corpus and outputs; reproduce re-grades the published outputs and re-runs lanes without model usage exactly.

**experiment.json** (validated by `experiment.py`; error names the field):

| field | rule |
|---|---|
| `corpus` | path of the corpus folder, relative to the experiment file; the flag `--corpus` (or `KOGEN_LANES_CORPUS`) replaces it, and `lanes-plan` records the resolved path in the run dir (`probe-corpus.json`, private) for `lanes-run` and `lanes-cell` |
| `items` | optional list of item ids: run only these (default: every item) |
| `lanes[]` | `{"name", "probe": {"command": [argv…], "args": {…}}}`; optional `"dry_run_ok": true`, `sha` (a Kogen commit for later pieces), `settings.models` (names the provider the lane's spend counts against, as for Kogen lanes; otherwise ChatGPT: it is the authority, and a usage row naming another provider makes the cell `bad_output`). No patch |
| `grader` | `{"kind": …}`, below |
| `reps`, `deadline_s`, `cost_cap_usd`, `provider_caps` | as for Kogen experiments; `hosts` is optional and every host must be local (probe cells never go over ssh); `kogen` is optional and ignored; `tasks` and `intent_form` are refused |
| `split` | optional `{"train": [ids], "test": [ids]}`, disjoint, together exactly the items; needed by `keep_revert` |
| `decision_rule` | `descriptive`; `task_sign`; `keep_revert` (needs `split`) |

**Corpus folder**: `items.jsonl`, one item per line `{"id", "input": {…}, "expected": {…}}` (other keys such as `meta` are kept and ignored), plus any files an input refers to, for example `repos/<id>/`. `lanes-plan` writes into `PLAN.json` the tree hash of the whole corpus folder and a hash of each item line, and for each lane the hash of its `probe` object and of every command element that names a file or folder (by argv index, so no path is written), likewise for the `command` grader. **Command paths**: an element that exists relative to the experiment file's folder is made absolute against that folder (the command itself runs in an empty temp dir), so a probe script can sit next to `experiment.json`; absolute paths work too; `lanes-plan` records the experiment's folder in the run dir. `lanes-preflight` (and `lanes-run`) refuse a first element that is not an executable on the resolved path or `PATH`, and an element written as `./x`, `../x` or an absolute path that does not exist. `lanes-run` verifies all the hashes and refuses (exit 2) if the corpus, an item, a command file or the grader changed; `lanes-cell` re-checks its item's hash.

**Cell** = (item, rep, lane): `cells/<item>/r<rep>/<lane>/`. The lane command runs in its own process group under `deadline_s` (TERM, then KILL of the whole group, also for stragglers of an exited leader), in a fresh empty temp directory, with the environment plus `LANES_CORPUS` (the corpus folder) and `LANES_PROBE_ITEM_DIR` (the folder `input.dir` or `input.repo` names inside the corpus, else the corpus); both are read-only by convention. Stdin is `{"input": item.input, "args": lane.probe.args}`; `expected` is never given. Stdout is `{"output": {…}, "usage": [{"model", "provider", "input_tokens", "cached_input_tokens", "output_tokens", "reasoning_tokens"}, …]}`; `usage` is optional (a probe that runs no model costs nothing), counters are non-negative integers or null (null counts at the cost guard's fallback allowance).

Files: `result.json`, `stdout.raw`, `stderr.txt`, and for a valid reply `output.json` and `evaluation.json` (`{grader, metrics: {name: number}}`). `result.json` is `{cell, lane, phase: "probe", exit_code, outcome, detail, started, ended, wall_s, cpu_s, peak_rss_kb, host, stderr_tail, usage, stages: [], totals}`: `cpu_s` is user plus system time of the command and the descendants it waited for (`wait4` rusage), `peak_rss_kb` the largest resident set among them, `stderr_tail` its last 2000 bytes, `totals` `{requests, the four token sums, wall_s, cost_usd}`. `outcome`: `ok`, `timeout` (exit 124), `exit_<n>`, `exec_error` (exit 127: cannot start), `bad_output` (stdout or usage not as above), `grader_error` (the output cannot be graded).

**Cost**: `cost_usd` prices `usage` as the cost guard prices Kogen requests (price table, unpriced model at the highest rates, null counters at the allowance). The guard sees a probe's spend when its cell ends (no live spend): `check_start` before each cell and the soft cap work as for Kogen cells; the hard cap cannot interrupt a running probe, so keep `deadline_s` short for a probe that spends.

**Graders**:
- `set_recall_precision_at_budget` (optional `sets`, default every list in `expected`): output `ranked` is a list of `{"path", "tokens", "start"?, "end"?, "symbol"?}`; it is cut to the longest prefix whose tokens sum to at most `lane.probe.args.token_budget`, else `input.token_budget` (no budget: not cut). An expected set holds paths (strings) or objects with `path` (symbols add `start`, `end`). File level: precision and recall of the distinct claimed paths against the set's paths. Symbol level, for a set whose objects have `start` and `end`: a claim with `start` and `end` hits an expected symbol on the same path when the line ranges overlap (inclusive); recall is the share of expected symbols hit, precision the share of range claims that hit one (a claim without a range makes no symbol claim); no claim gives precision 0. Metrics `<set>.file.{recall,precision,f1}`, `<set>.symbol.{recall,precision,f1}`, `tokens_used`, `items_kept`. A mechanism that returns whole files (claims with no `start`/`end` or symbol) makes no symbol claims, so it scores near 0 at symbol level by design; compare such a mechanism on the file-level metrics. An absent or empty expected set (for example `read_files`, which exists only for real runs) is normal: the item has no metrics for that set, and `evaluation.json` lists it under `undefined` with the reason (`expected set empty` or `expected set absent`).
- `exact_match` (optional `keys`): `exact` is 1 when the output (or those keys) equals `expected` as JSON (`1` equals `1.0`, `true` does not equal `1`), else 0.
- `command`: `grader.command` gets `{"item": …, "output": …}` (the item with `expected`) on stdin, under `grader.deadline_s` (default 60), and prints one JSON object of numbers, the metrics.

**Report** (`report.json`, `report.md`): per lane the outcome counts and, per metric, the mean over items of each item's mean over its ok reps, with a Student t 95% interval over items (the item is the unit); the metrics are the grader's plus `wall_s`, `cpu_s`, `peak_rss_kb`, `cost_usd`; then the cost section of the Kogen report. Only ok cells count. Per metric the report gives how many items it covers and how many were left out, with the reason (`no ok cell`, `expected set empty`, `expected set absent`, `not reported by the grader`). Rules, over items, on `decision_rule.metric` with `baseline` and `candidate` lane names and `better` (`higher`, the default, or `lower`): `task_sign` (`min_gain` in metric units, default 0; `max_p`, default 1) counts items where the candidate beats the baseline against the opposite, exact one-sided sign test, `keep` / `reject` / `unresolved`; `keep_revert` (`min_effect`, `range` the width of the metric's range, default 1; optional `improves {"test": "task_sign", "max_p": p}`) applies the climb rule per split with the item as the unit and a Hoeffding interval of that range, `keep` / `revert` / `within_noise`. An item in the rule's scope with no ok cell on a lane makes it `incomplete`; an item whose metric is undefined (above) is left out of the rule, not counted as a missing cell, and the verdict line says how many were left out and why; a metric no cell has makes it `invalid_rule`. There is no noise gate for probes.

## Claude Code executor (the subscription route)

Kogen a54aa260 can run its builder as the installed Claude Code (CC) CLI, signed in with a subscription (`docs/configuration.md`, "Build executor"; `docs/executor-contract.md`). Its adapter strips tokens and API variables from the child, passes `CLAUDE_CONFIG_DIR` and gives the child Kogen's own `HOME`.

- **Role string.** A lane role `"claude-code/<model> <effort>"` (for example `"build": "claude-code/claude-sonnet-5-5 medium"`) is written to `.kogen/project.yaml` as `<role>: {executor: claude-code, model: <model>, effort: <effort>}`, with no `provider`. Kogen a54aa260 accepts it on `build` only (`shape`/`review` with an executor are `environment/project_config_invalid`); lanes does not block other roles. All of the role-string-to-keys mapping is `cell.role_entry`, so a change of Kogen's keys touches that function only. Other provider strings are unchanged.
- **`CLAUDE_CONFIG_DIR`** comes from the hosts file, per host: `"claude_config_dir": "<folder holding the CC login>"` (required on every host of a run with a claude-code lane, because the folder differs per machine). `lanes-run` sets it in the environment of the Kogen of every cell of such a lane, on local hosts (the `lanes-cell` process) and remote ones (the ssh command), and for no other lane. `HOME` is not changed: cells keep the one the process has, which the operator sets to the lanes Kogen home. Optional `"claude_bin"` names the `claude` executable (else `$CLAUDE_BIN` on a local host, else `claude` on `PATH`); Kogen looks `claude` up on `PATH`, so its folder goes first on the `PATH` of those cells.
- **`cell_memory_max`** (optional, per local host, like `"4G"`: digits with an optional `K`, `M`, `G` or `T` suffix, powers of 1024) caps the memory of each cell on that host, so a runaway stops its own cell and nothing else; absent, cells are not capped. A remote host with it is refused. `lanes-run` logs one line per host naming the mechanism. On Linux with cgroup v2 and a delegated cgroup (a systemd unit started with `-p Delegate=yes`, whose `cgroup.subtree_control` the process can write) each cell runs in its own child cgroup with `memory.max` set and `memory.oom.group=1`, so the kernel kills the whole cell together; `lanes-run` moves itself (and any other process of its unit) into a `dispatch` leaf first. Otherwise (macOS, an undelegated cgroup) a watchdog sums the resident set of the cell's process tree (`ps -A -o pid=,ppid=,rss=`) every 2 s and, above the cap, sends TERM to the tree and KILL 3 s later. Either way the cell dir gets `memory-cap.json` `{cap, peak_rss, at, mechanism}` (bytes) and, when the cell left no `result.json`, one with `outcome: "memory_cap"` and its spend; the run goes on with the next cell. `lanes-report` classes such a cell `incomplete` and counts it as plumbing `memory_cap` (like `cost_cap`, not a model failure).
- **Preflight.** For such a run, `lanes-run` (unless `--skip-preflight`) and `lanes-preflight --hosts <hosts file>` check each of the experiment's hosts before any cell: `claude_config_dir` set and an existing directory, then `claude auth status --json` run as a cell would (the host's own `HOME` and environment, minus `KOGEN_LANES_*` and the variables Kogen strips, with `CLAUDE_CONFIG_DIR` set) must report `loggedIn: true`. One line per host, `claude-code preflight: ok|REFUSED: <host>: <reason>`; nothing the command printed is shown. Any refusal stops the run (`lanes-run` exit 2, `lanes-preflight` exit 1); without `--hosts`, `lanes-preflight` refuses a claude-code run.
- **Cell cap.** CC use is not priced, so the USD guard cannot see it. A lane whose roles use the prefix counts its cells under provider `claude-code`, so `"provider_caps": {"claude-code": {"cells": N}}` is required to start cells and stops new claude-code cells after N, exactly as for other providers (`lanes-run` exit 3, "claude-code cell cap reached"). Read the seat's own usage before and after a run. A lane may pair the executor with one priced provider (for example a CC build and an `anthropic/…` review): its cells count against both providers' caps, its dollars and rate-limit stops against the priced one, so it needs both `provider_caps` entries.
- **Dry cell.** `lanes/bin/lanes-ccdry <run-dir> --tasks <tasks> --hosts <hosts file> --host <name>` runs exactly one cell (the first unfinished one of a claude-code lane, with the preflight above) on that host, then reads the cell's saved Kogen run log (`run-log/log.jsonl`). It passes (exit 0, `ccdry: ok`) only if the log has an `executor_started` event for `claude-code` and an `executor_round_started` event. It fails (exit 1) when Kogen fell back to a native provider (build `request` events, no executor events), when the executor never started, or when the cell did not finish. Run it once per host before a measured run. `lanes-run` also takes `--only-host`, `--max-cells` and `--claude-code-only`, which it uses.

## Cost cap

`cost_cap_usd` is the **soft cap**; the **hard cap** is 1.25 × `cost_cap_usd`. Both come from `experiment.json` (so `PLAN.json` carries the cap) and are enforced in `lanes/lanes/costguard.py`, which every entry point uses. A run dir whose `experiment.json` has no `cost_cap_usd` (an older run) gets no new cell from `lanes-run` or `lanes-cell`; the error says to add the field and run `lanes-plan` again.

**Per provider.** `cost_cap_usd` applies to the spend of ChatGPT lanes only. Other providers (`opencode-go`, `supergrok`, ...) have `provider_caps`: `cells` caps the cells started (a cell dir or a ledger line counts) for the provider's lanes, `usd` is a soft/hard dollar cap like the ChatGPT one. A cap blocks new cells of its own provider only; a provider's estimated dollars without a `usd` cap are reported and never stop a run. A hard cap stops the running cells of its own provider only (local cells stop themselves; `lanes-run` halts the rest after 3 s). `lanes-run` exits 3 when a cap left cells unstarted.

**Rate limits.** After each cell, its saved logs are checked for a failure on a limit, using the records Kogen writes (`provider_failure` is `{http_status, code, type, event_kind}`; OpenCode Go and ChatGPT/SuperGrok both write it): a build `outcome` event's `provider_failure` (written after Kogen's retries failed, so a 429 a retry recovered does not count); a shaping `provider_call` that failed (`error` set) with `provider.provider_failure`; in `stdout.txt`, Kogen's `provider failure: {json}` line and its `provider/<reason>:` error line when the reason names a limit (`usage_limit`). A record is a limit when `http_status` is 429 or its `code`/`type` contains `usage_limit`, `rate_limit` or `too_many_requests`; an event's `error`, `reason`, `code` or `outcome` class naming one counts too. Documented fallback, only where Kogen gives no class: a `provider/<reason>:` stdout line whose detail says `HTTP 429`. The first limit writes `rate-limit-stop.json` in the run dir (`{provider: {cell, reason, rate_limited: true, at}}`, never replaced by a later one), before the cell is released, so no slot starts another cell of that provider; `lanes-run` then starts none (exit 4 when cells were left) and `lanes-cell` refuses (exit 2); other providers go on. It is not cleared automatically: delete it after the limit resets.

**Spend estimate** of a run dir: finished cells' `totals.cost_usd` (a null one is re-read from the cell's saved logs), plus the spend so far of running cells parsed with `usage.py` from their live Kogen run log and shaping events, plus the **ledger**. A running cell leaves `live.json` in its cell dir (`workspace`, and the `pid` and `start` time of its lanes-cell, its `host` name and the `node` it runs on); a cell that stopped without `result.json` leaves `spent.json`. Spend is never forgotten: before a cell dir is thrown away (a retry, `--force`), its spend is appended to `cost-ledger.jsonl` in the run dir (`{cell, usd}` per line) and counted from then on; a remote attempt that was killed has its `spent.json` fetched into the ledger before the remote dir is removed (the last polled value is the floor).
- no price row for the model (or no price cost_calc can give): the request's tokens at the rates of the priced model that `reproduce/guard-estimates.json` names for it (`{"models": {model: {"as": priced model, "note": why}}}`, e.g. an unpriced new model estimated at another model's rate; the price table is hash-pinned, so the map is a separate file, and `as` must have a complete row in it), else at the highest input, cached-input and output rate in `reproduce/price-table-v1.json`. This is for the guard's spend estimate only: reported costs (`cost_calc`, records, `result.json` totals, exports) never read the guard estimates, so an unpriced model stays unpriced there (`cost_usd` null, `cost_reason` `unlisted_model`) and no list price is invented;
- unknown usage (a null counter, or a build request whose four counters are all 0): an allowance of 100,000 input and 20,000 output tokens at those rates (about $2), above the largest request seen in real logs (53,940 uncached input tokens). It is an allowance, not a proven bound.

**Phantom cells.** A cell that dies hard (`kill -9`, a stopped run unit, a cgroup memory kill) cannot remove its `live.json`. `live.json` fields: `workspace`; `pid`; `start` (the process start time: `ticks:<n>`, field 22 of `/proc/<pid>/stat`, on Linux, else `lstart:<ps -o lstart=>`); `host` (the hosts-file name); `node` (the machine's hostname; a `live.json` of another node is never judged). A `live.json` is a **phantom** when its `pid` is not alive, or is alive with another `start` (the pid was reused). One from before these fields (workspace only) is a phantom only when its workspace folder is gone. Before every spend read (`costguard.snapshot`, so the cost guard, the watcher and the host gate of `lanes-run`) and before each cell is claimed, `costguard.reap_phantoms` reaps each phantom under the run dir's exclusive lock: it writes `spent.json` `{"usd": <upper estimate>}` (kept as is when the cell already has a `result.json` or `spent.json`), moves `live.json` to `live.json.reaped`, and logs `<host>: reaped phantom cell <cell> (pid <p> gone; spend settled at $X, upper estimate)`. The estimate is the spend the cell's workspace logs still show when the workspace is there; otherwise the larger of `PHANTOM_REQUESTS` (5) unknown-usage requests (`FALLBACK_TOKENS` at the top rates, about $2 each) and the mean cost of the run's finished cells. The cost guard then reads the cell through `spent.json` and does not fail closed; the workspace folder of a reaped cell is left on disk.

**Host gate.** Optional, per machine. A file `host-cap` next to the `runs/` folder (`<runs>/../host-cap`) holds `<cap> [<load factor>]` (for example `6 0.8`; cap 0 or an unreadable file: no cap; factor default 1.0). With no such file nothing is gated. With it, before a `local` slot takes its next cell `lanes-run` waits while the machine's 1-minute load average is above CPUs x factor, or while the live cells have reached the cap. Live cells are counted across every run: each `<runs>/*/cells/*/*/*/live.json`, plus each running `lanes-grade` process. One admission at a time across all runs (`flock` on `host-cap.lock`), then a 20 s settle so the new cell's `live.json` is counted by the next one. The first hold of a wait is logged: `<host>: holding the next cell (load L > N cpus x F, or live K >= cap C)`. Before counting, the gate reaps the phantoms of every run dir under `<runs>/` that has a `live.json`, each under that run's own lock (see Phantom cells), so a cell killed hard in another run does not hold a place. A `live.json` beside a `result.json` is a leftover: it is moved to `live.json.stale-finished`, with no change to the spend.

**Fails closed on real errors**: unreadable or unparsable usage (a log line that is not a JSON object, other than a last line still being written; counters that are not non-negative integers or cached > input; a malformed `result.json`, `spent.json` or ledger), no `cost_calc.py` or price table, or a crash of the guard stops the run. `lanes-cell` refuses to start (exit 2, "fails closed"); a running cell is aborted as `cost_cap` (`result.json` has `cost_error`); `lanes-run` claims no new cell and stops every cell.

**Exactly once**: a source that is gone because its attempt finished, was retired or was cleaned up is not an error. Every step that moves an attempt's spend from one record to the next holds the run dir's lock (`flock` on `.cost.lock` in the run dir) exclusively: a cell ending (`spent.json` written and `live.json` removed before its workspace is deleted; `result.json` is written while `live.json` still exists and is read first), `retire` (ledger line, then the cell dir removed) and every ledger append. `estimate` reads under the shared lock, so it sees each attempt in exactly one record. A source gone with no final record yet (a `live.json` whose workspace is gone, no `spent.json`) is retried, with the lock released, for 5 s (`RETRY_S`); then the guard fails closed. On the controller, an attempt's remote live spend and its ledger line change together under one lock (only cells still running keep a polled value).

**Soft cap**: `lanes-run` claims no new cell once the estimate is at or above the cap, and exits 3 when cells were left; `lanes-cell` exits 2 without starting when the estimate has reached it. Both print the spend and the cap and write `cost-stop.json` in the run dir (`{cap: soft|hard, spent_usd, at}`; a hard note is never replaced by a soft one; a new `lanes-run` clears it).

**Hard cap**: while a cell runs, a watcher thread in `lanes-cell` (every `LANES_COST_WATCH_S` seconds, default 0.5) kills the cell's own process group as soon as the run dir's estimate reaches the hard cap. The cell is recorded with outcome `cost_cap` (also the killed command's stage outcome); the report counts it as plumbing, not a task failure (class `incomplete`, plumbing category `cost_cap`, also a key of a climb report's `plumbing_counts`). `lanes-run` writes the note, stops claiming, gives local cells 3 s to stop themselves, then stops every cell it started, and exits 3.

**Remote hosts**: `Host.prepare` copies `reproduce/cost_calc.py`, the price table and `guard-estimates.json` to the host (`<root>/reproduce/`). While a remote cell runs, the controller polls `python3 -m lanes.costguard cells <remote run dir>` over ssh every second and adds each cell's live spend (the larger of the local and the polled value) to its own estimate, so the soft and hard caps cover cells on every host. Three polls in a row that fail stop the run (fail closed). Every remote host is polled. A remote `lanes-cell` also guards its own host's cells.

`lanes-cost recompute <run-dir>` rewrites the cost fields of finished cells from their stored logs (`cost-backup.json` per cell keeps the old values) and removes `cost-stop.json` when no USD cap is reached any more; see README, "Cost guard". A cell's stage records and `totals` carry `model_sources` (`effective` or `configured`: the log's `effective_model`, else its `configured_model`; null names are never invented, the reason is then `model missing`). A price row whose rate for one component is null prices that component at the table's highest rate (reason `fallback_rate: <component>`). Rates are short-context; a row's `note` says when a provider's long-context tier is not modelled (`grok-4.7` above 200K tokens).

`report.json` has `cost`: `{cost_cap_usd, hard_cap_usd, spent_usd, lanes: {lane: usd}, lane_providers, providers: {provider: {spent_usd, usd_cap, hard_cap_usd, cells_started, cells_cap, rate_limited}}, cost_cap_cells, not_started, stopped}`; `stopped` is `hard` when any cell ended `cost_cap` (a remote cell's own note stays on its host), else `soft` or `hard` from `cost-stop.json`, else null; `not_started` counts planned cells with no cell dir. `report.md` has the section "Spend vs cost cap".

## `lanes-leakcheck`

Compares a lane's added text (patch `+` lines and target paths, and settings) with what only the
tasks know. Only added text can leak: a string literal or hidden-test line is skipped when it occurs,
whitespace folded, anywhere in the base prompt surface (the files under `cli/agent/prompts/` of the
Kogen the lane is built on, `--kogen DIR` or the clone at the lane's sha, plus the patch's own context
and removed lines), even when the patch rewrites the line around it or moves it. This substring rule
does not extend to the rest of Kogen's source, because a task made from a reverted Kogen feature can
have its solution there; the older whole-identifier and whole-literal exemptions for Kogen's source
are unchanged. New wording is still compared. There are no per-hit exemptions.

## Task folder (private)

Lab layout, e.g. `$LAB_NEXT/spec/examples/tasks/rate-go`; schemas `spec/schema/task.json` and `evaluate.json`. Outside the repo; the harness takes its path from a flag or `KOGEN_LANES_TASKS`. `lanes/tests/fixtures/task-mini` is a tiny Go task valid against both schemas.

- `task.toml` (`task.json`): required `name` (l.4), `split` (`development` | `confirmation`, l.8), `language` (l.16), `requires` (list, l.20), `test_globs` (list, l.55), `regression_tests` (list, l.59); optional `env`, `setup` (list), `fix` (list), `protect` (list), `[[check]]` {`name`, `run`} (both required, l.36), `[acceptance]` {`run`, `steps_dir`}; `approve_timeout_s` (whole seconds, 1 to 3600; default 120): the deadline `lanes-preflight` gives `kogen intent approve` for this task, for tasks whose readiness runs a long test suite. Any other value (not an integer, 0 or negative, over 3600) is refused by `lanes-preflight` and `lanes-cell`. It does not change the cell deadline (`experiment.json` `deadline_s`) or the acceptance check of `lanes-qualify`.
- `start/` — the starting tree (the work tree's first commit); includes the acceptance steps folder (`features/steps/`).
- `reference/` — a correct solution, files copied over `start/` (the fake Kogen's `correct` mode).
- `wrong/<name>/` — known-wrong solutions copied over `start/`; the grader must fail them.
- `evaluator/` (`evaluate.json`): `evaluate.toml` with required `overlay` (`evaluate.json` l.7; folder under `evaluator/` laid over the tree, normally `files`) and `[[command]]` (at least one, l.11) each with required `name`, `run`, `adapter` (`go_test_json` | `exunit_lab` | `lab_jsonl`), `results` (file the command writes via `$LAB_RESULTS`) and `timeout_seconds` (int ≥ 1); optional `setup` (list) and `[expected]` {`requested`, `regression`} (lists of test ids). Hidden tests live in `overlay`.
- `LANES_SHARED_GOCACHE` (environment variable, optional): a directory for one Go build cache shared by all grading trees. When set, every grading command (setup and evaluator lines) has any inline `GOCACHE=<word>` rewritten to `GOCACHE=<that directory>` and runs with `GOCACHE` set to it; the Go build cache is content-addressed, so sharing it does not change results, and large or vendored codebases are not recompiled for every grade. Unset, commands run exactly as written. Evaluator commands should not set `GOCACHE` themselves (`lanes-qualify` warns when one does).
- `request.md` — the shape brief (`shape` and `e2e`).
- `supplied/<form>/` — the frozen approved Intent, one folder per Intent form: `intent.md`, `acceptance.feature` and the step files the Intent's `Acceptance:` list names (e.g. `features/steps/…`); `gherkin-lean` adds `model.lean`, `gherkin-quint` adds `model.qnt`; `prose` has only `intent.md`. Forms: `gherkin`, `gherkin-lean`, `gherkin-quint`, `prose` (`$LAB_NEXT/spec/examples/tasks/rate-go/supplied/`, `EQUIVALENCE.md`; chosen in the Lab by `shape.supplied`, `spec/schema/config.json` l.740–749). A `build` experiment names the form in `intent_form`.

### `lanes-qualify`

`lanes-qualify [--kogen PATH] <task-dir>...` prints one line per check, `ok   <task> <check>: <detail>` or `FAIL <task> <check>: <detail>`, and exits 1 if any line fails. Checks, in order: `reference`, `start`, `wrong/<name>` (one per known-wrong tree), `emptied overlay`, `acceptance`, `intent`, `determinism`.

- `intent` asks Kogen whether the supplied Intent is acceptable, as `lanes-preflight` will: the Intent goes into a scratch workspace made from `start/` and `kogen intent approve <slug>` runs, then again with the printed hash, within the task's `approve_timeout_s` (default 120 s). Approval prints `ok   <task> intent: approved <hash8>`. A refusal prints `FAIL <task> intent: approve refused (exit N):` followed by Kogen's lines (for example `intent/lint:` errors such as a title over 50 characters, a missing or empty `## Tests` section or a missing `## Feasibility` section). The `gherkin` form is always checked; `gherkin-lean` and `gherkin-quint` are checked when `supplied/<form>/` holds both `intent.md` and `acceptance.feature`, each on its own line named `intent/<form>`. Kogen refuses an Intent that has no `acceptance.feature`, so a form without one (`prose`) is not checked and prints no line, as for a form that is absent; it never fails the check. No model provider is called.
- The Kogen comes from `--kogen PATH` (an executable, a release folder or a `.tar.gz`), else the `KOGEN_BIN` environment variable. With neither, the line reads `ok   <task> intent: skipped: needs --kogen or KOGEN_BIN in the environment` and does not change the exit code, as for an `acceptance` check that needs a missing `KOGEN_*` runner variable.
- A command that sets a per-tree `GOCACHE` inline (a value under `$PWD` or another relative or tree path, e.g. `GOCACHE=$PWD/.cache/go go test ...`) prints `warn <task> evaluator: per-tree GOCACHE in command N recompiles every grade; drop it (the harness supplies a shared cache via LANES_SHARED_GOCACHE)` after the check lines. It is a note only: it never fails a check and does not change the exit code. Absolute paths, `~`, `$HOME` and `$LANES_SHARED_GOCACHE` values are not flagged.

## Run directory

`$KOGEN_LANES_HOME/runs/<experiment id>/` (`KOGEN_LANES_HOME` defaults to `~/.cache/kogen-lanes`):

```
experiment.json  lanes.lock.json  plan.jsonl
cells/<task>/r<rep>/<lane>/
  result.json  run-log/  final-tree.tar  intent/  stdout.txt  stderr.txt  evaluation.json
```

- `result.json`: `{cell, lane, phase, exit_code, outcome, started, ended, wall_s, kogen_version, node: {path, version} | null (the Node of an unpacked release's `node-path`), final_tree, pass_trees: [], first_green_tree: <tree id> | null, intent_hash, host, stages, totals}`; `stages` and `totals` are described under Stage records.
- `run-log/`: copy of Kogen's run folder. `final-tree.tar`: `git archive` of the final tree. `intent/`: the Intent (shape and e2e).
- `evaluation.json`: added by the grader (L4). Build cells also list `pass_trees: [{tree, ...}]`, one entry per tree id of `result.json`, each graded like the final tree (`all_passed`, ...), or `{tree, ungraded: "tree not available"}` when `pass-trees/<id>.tar` is missing. The entry of the first green tree has `first_green: true`; no other entry has the field.
- `e2e` cells keep every build key above and add `shape`: the grade of the Intent the cell shaped, with the keys a `shape` cell's `evaluation.json` has (`phase`, `infrastructure`, `matrix`, `scenarios`, `pass_on_reference`, `fail_on_start`, `wrong_caught`, `wrong_total`), run on the cell's `intent/` as for a shape cell. When the shape stage did not finish (refused, questions pending, timed out), or the cell has no Intent or its step files are missing, `shape` is `{phase: "shape", infrastructure: <reason>}` with no counts. Its `infrastructure` never marks the cell's build grade; the top-level `infrastructure` stays the build's. A cell graded before this field existed has no `shape`. `lanes-report` adds `shape` (summed counts) and `shape_classes` (`correct`, `incorrect`, `infrastructure` per cell, by the shape rule) to an e2e lane, and `lanes-export` publishes only its existing keys.
- `pass-trees/<tree id>.tar`: `git archive` of each pass tree the workspace still holds, written when the cell ends.

**Pass trees and the first green tree.** `pass_trees` lists, in log order and without repeats, the `tree` of every `review`, `commit` and `stage_pass` event and of every `pass` event that has `green: true` and a `tree`. A red `pass` tree is not listed. `first_green_tree` is the tree of the first green `pass` event that carries a `tree`: the candidate that first passed verification, before any reviewer edit, so a round can grade it besides the final tree. In a staged build only the `pass` events after the last `stage_pass` count (earlier ones check one stage's commands, not the whole Intent). It is null when the log has no such event: a Kogen whose `pass` event carries no tree, or a build that never went green. It also appears in the public cell record when `result.json` has it. The first green tree can equal the final tree (no reviewer edit); its entry is still marked.

## Stage records (`result.json` `stages`, `totals`)

`lanes/lanes/usage.py` (`parse_run_log(events, commands, table=None, shape_events=None)`) builds them from two sources: the build run log (`events`) and the shaping events (`shape_events`: `.kogen/local/shaping/<slug>/events.ndjson`, which `kogen intent shape` writes; `shape.ex` l.11, `shape_evidence.ex` l.59–90). **L3 copies the shaping events file into the cell** (next to `run-log/`) for every cell that ran `shape`. Every phase records them, shape-only cells too, because identical Intents still differ in cost and speed. `commands` is one entry per Kogen command the cell ran, `{stage, started, ended, wall_s, exit_code, timed_out?}`, measured by the harness, so each command's wall time exists even when the log is silent.

`stages[]`, in command order, each `{stage, started, ended, wall_s, exit_code, outcome, requests, models, input_tokens, cached_input_tokens, output_tokens, reasoning_tokens, cost_usd, cost_reason, missing}`:

- `stage`: `shape`, `approve` or `build` (command level; `shape` sums the `provider_call` events of the shaping events, one request each, model = `effective_model`, usage `{input, cached, output, reasoning}` with nulls kept as null, `wall_ms`; `started`/`ended` are ISO-8601 UTC, `wall_s` seconds, `exit_code` the command's), then one inner record per request role the log names `verify`, `review`, `repair`. An inner record has the tokens, cost and the summed request `wall_ms` of that role; `started`, `ended`, `exit_code` and `outcome` are null and listed in `missing`. A request belongs to exactly one record: `build` holds every request not in an inner role.
- `outcome`: `timeout` when the command hit its deadline; for `build` the last log `outcome` event (`landed`, `build_blocked`, ...), `no_outcome` when a build that exited 1 logged none, else its exit code's class (`provider`, `environment`, `dirty_tree`, ...); otherwise `ok` or `exit_<code>` (`approve` exit 5 with a card counts as `ok`: it printed the card).
- Tokens are sums over the stage's requests (`reasoning_tokens` is a subset of `output_tokens`). A request with a null counter (shaping events when the provider sent no usage; build logs of a future Kogen) makes the stage's sum null. A build request whose four counters are all 0 is flagged, not priced (see the R2 gaps): `usage_zero_is_unknown` in `missing`, `cost_usd` null. `approve` makes no request: zero tokens, cost 0.
- **Seeded build**: when the run log has a `seeded` event, a declared seed replaced the builder, so a `build` stage with no request has zero builder requests by design. Its tokens count as 0 and its `cost_usd` is 0 with `cost_reason` `seeded: no builder request by design`; nothing is listed as missing for it. The rule applies to the `build` stage only: without a `seeded` event, no request still means null tokens and `cost_usd` null (`no request in the log`), and `shape` and `approve` are unchanged. A seeded build that does log requests is priced from them as usual.
- `cost_usd`: sum of `reproduce/cost_calc.py` over the requests (model id as logged, else the part after `/`); null with `cost_reason` when usage is missing or a model has no price. When cost_calc prices a model from a third-party rate it returns an estimate: `cost_usd` keeps the value and `cost_reason` is cost_calc's status (`declared_estimate`), so an estimate is never reported as exact. Totals join the reasons.
- `missing`: names of the null fields the log could not supply. Nothing is invented.

`totals`: `{requests, models, input_tokens, cached_input_tokens, output_tokens, reasoning_tokens, wall_s, cost_usd, cost_reason, missing}`. Counters and cost sum all records (null when any is null); `wall_s` sums command-level stages only, since inner records overlap them.

**R2 gaps** (what b45ba32b's log cannot supply, so these fields are null and listed in `missing`):
- Build `request` events log `ChatGPT.usage/1`, which turns every missing counter into 0 (`chatgpt.ex` l.651–661): a request whose provider sent no usage looks like a request with zero tokens, and the log cannot tell 0 from unknown. The harness therefore flags a build request with all four counters 0 (`usage_zero_is_unknown`, cost null) and R2 would add a null or a flag. Only the shaping events (`known_usage`) carry null counters.
- The shaping events file is not a run log: it has no outcome and its events are not in the build log, so the harness reads it separately (above).
- No stage start/end events: `started`, `ended` and `exit_code` come from the harness, and inner stages have none.
  Inner stages other than `review` are named only if a request role says so; `repair` and `verify` appear only then.
- No per-request start time in the build log (only `at` at the end and `wall_ms`).
- Build outcome beyond the last `outcome` event, and distinct exit codes per outcome, as listed under Not in b45ba32b.

## PLAN.json

Written by `python3 -m lanes.plan_hashes <experiment.json> --tasks <dir> --lock lanes.lock.json --out PLAN.json` before any cell runs, and committed to kogen-bench before the run. It holds only hashes for private material:

```
{experiment: <experiment.json>,
 hashes: {tasks: {<id>: {task, tree, hidden_tests, task_toml, request, intents: {<form>: sha}}},
          lanes: {<name>: {patch, settings}}},
 lock: {sha256, artifacts: {<lane>: artifact_sha256}}}
```

`task` is the whole task folder (so `reference/` and `wrong/` are covered too), `tree` the `start/` tree, `hidden_tests` the `evaluator/` folder, `intents.<form>` each `supplied/<form>/`, `patch` the patch file (null without one), `settings` the sha256 of the lane's settings as sorted compact JSON. Folder hashes are `common.sha256_tree`; file hashes `common.sha256_file`.

`PLAN.json` omits the experiment's `hosts` (host names never go into the public repo). `plan_hashes` exits 2 with a message, writing nothing, when a task folder, its `start/` or `evaluator/` is missing, when a build or e2e experiment's `intent_form` has no `supplied/<form>/`, when `request.md` is missing for a `shape` or `e2e` experiment (it is optional otherwise, hash null), when the lock is not a list of entries with `name` and `artifact_sha256`, or when a lane has no lock entry.

### Publication marker

Only at publication time, `lanes-export --publish-private` adds `"publication": {"closed": true, "closed_at": "<UTC>", "files": {"<path relative to the round>": "<sha256>"}}` to the round's `PLAN.json`; `hashes` and everything written before the run stay untouched. `files` lists every file under `reproduce/tasks/<task>/evaluator/` (hidden tests included). The export refuses, publishing nothing, when a published `evaluator/` folder no longer hashes to the task's pre-run `hidden_tests`. A re-run keeps the first `closed_at`. The release validator reads this marker (`reproduce/VALIDATION.md`). Adding it changes the file hash of `PLAN.json`; the export therefore rewrites each `records.jsonl` `manifest_sha256` that named the earlier `PLAN.json` to the published file hash.
