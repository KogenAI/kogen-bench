# kogen-loop vs Codex: what the published evidence shows

Scope: every published comparison between kogen-loop (Kogen's small, stand-alone coding agent, "loop" below) and Codex CLI. Source: the public kogen-bench repository and its per-result reproduction packs. Each row links to that result's page on this site, which carries the pack text and a link to the pack. All numbers are copied from those pages. No new runs. Written 31 October 2026.

Same-pair rule: in every row below, loop and Codex ran the **same model (gpt-6.1-terra) at the same effort** in the comparison itself. Where a row is not a loop-vs-Codex task comparison (route speed, analysis of old runs) it says so. "Effort" is the model's reasoning-effort setting (medium or high).

Common facts, unless a row says otherwise: Codex CLI 0.165.0; kogen-loop commit `b8a4046` (default build); one run per task and tool; hidden tests grade each final result; "API route" means both tools used the same API key through one gateway, so cost is at list prices from per-request receipts; hosts are cloud Linux servers, one run at a time. Core counts are published only for the apply_patch row.

- **Sample sizes are small.** Most rounds are 3 to 24 tasks with one run each, so sign tests can only detect large effects. Row 3 has n=4 (the smallest possible p is 0.125); row 6 has 5 pairs; row 8 has 8 runs per tool. Pages state test power where known: row 2 about 0.75 for a 20% effect, row 4 about 0.75 for a 10% effect and under 0.05 for a 1-3% cost effect, row 5 about 0.79 for a 30% effect only, row 1 about 0.3 for a 20% cost cut in the replay test. "No effect seen" is not "equal".
- **Confidence intervals** are not published for these rows; the pages give sign-test p-values and counts instead.
- **Repetitions are not independent tasks.** Row 4 uses 3 tasks x 6 repetitions, so the effective sample is 3 tasks and the page says the p-values overstate the evidence. One of its tasks (`revive-baseline-go`) failed in all 12 loop runs and passed in 1 of 6 Codex runs (p=0.33); the failing hidden test was never diagnosed; all of the 6.6% lower cost per pass of the verbosity arm comes from that task. Row 5 reused tasks from earlier rounds. Row 2 and row 7 used a rotated or fixed order within a task, not a random one, so order or caching effects are possible.
- **Task difficulty.** Rows 1 to 5 and 7 to 9 use short Go tasks; row 5 notes one task costs several times the others and dominates totals. Only row 6 uses hard tasks. Most task kits are withheld, so outside readers cannot rerun every row. Only 5 of the 24 tasks of row 9 are published.
- **One host per round, one run at a time.** Wall times depend on that host. Cost is at list prices from the gateway receipts, not an invoice.
- **Timing-host rules.** The published rule ([protocol-split-20261030](/findings/protocol-split-20261030/)) says loop-vs-Codex wall time and cost are claimed only from the Linux servers, interleaved per task; the Macs make no wall-time claim. Row 9 (subscription route, one Linux server) and row 12 (two Macs) predate that rule and carry route confounds: loop and Codex reached the model by different routes, and a provider-side speed change early on 30 October was not explained.
- **Two arms are patched experiments, not releases:** loop + reasoning replay, `batch`, `exec`, verbosity low, `apply_patch`, yielding shell. Comparisons of loop default vs Codex use the unpatched build.
- **Row 5**: the default arm's total includes one runaway run (hit the 128,000-token output cap and failed); without that block `apply_patch` cost 13% more (not registered in advance).
- **Row 6**: one block was cut by the spend guard, on the task that shows the tail, so the yield effect may be understated. Two default-shell runs hit the 3,600 s limit (counted as outcomes, wall censored at 3,600 s). 4 of 6 yielding cells ended on loop's 512 KB request limit.
- **Row 2 and row 3**: the loop binaries are rebuilds identified by hash, and the tool and its added instruction sentence are not separated.
- **Not included.** Rows where Kogen (the full product driving Codex) is compared with Codex alone on hard tasks, and the rule-only finding ([protocol-split-20261030](/findings/protocol-split-20261030/)), are outside "loop vs Codex" and are left out of the table. [loop-sub-route-honest-probe](/findings/loop-sub-route-honest-probe/) tests loop's own routes only (no Codex arm), so it is also left out.
